Naive re-render vs. incremental streaming

Both panes stream the same markdown, one chunk at a time. The left is the naive baseline every chat UI starts with — innerHTML-replace the at-rest render of the whole partial on every chunk. The right is StreamingMarkdownRenderer.update(), which patches the DOM incrementally and holds unfinished constructs in a pending state. Watch the jank counters diverge.

What the counters measure

Nodes added counts DOM elements created (via a MutationObserver on each pane). The naive pane re-parses and re-inserts the entire partial on every chunk, so its count climbs with the square of the document; the incremental pane only appends what changed. Layout shifts / CLS come from a PerformanceObserver({ type: 'layout-shift' }), attributed to whichever pane owns the shifted node — the visible jank of an unfinished construct flashing raw, then re-flowing when it completes.

  • Naive: **bold shows literal asterisks, a half table is a paragraph of pipes, [^1] is literal text — each flashes, then the whole subtree is thrown away and rebuilt next chunk.
  • This library: the unfinished construct is held in a pending state that already has its final layout, so completing it only recolours in place. This page doubles as a visual regression bed for that pending→committed motion contract (see ARCHITECTURE.md).
